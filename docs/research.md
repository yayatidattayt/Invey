## 0. Nonnegotiable product definition

This is **an installable Windows utility**, not a website and not a conventional gesture air mouse.

1. The user's **physical Windows mouse** continues operating normally, including its cursor, clicks, focus/drag semantics, and existing application workflow.
2. A separately rendered, webcam-hand-controlled **GHOST** has its own position, hover, press, drag and target state. GHOST must never secretly teleport or commandeer the real mouse cursor.
3. **POCKET** owns an immediately usable, slide-away, recallable shelf of selected screen content. GHOST fully operates Pocket-owned controls; the physical mouse can continue working underneath the click-through overlay.
4. **External Windows actions** are **capability-gated semantic operations** (UI Automation / separately verified application adapters), not universal second-native-mouse behavior.
5. Core use must work **offline**, with **zero paid inference**, without custom kernel drivers, and with camera-free keyboard/mouse fallback. The app should not demand elevation or disable Windows security protections.
6. A minimal, high-quality visual experience is part of the product; smoothness, focus preservation, privacy and reliability are release gates, not promotional claims.

**Fundamental boundary:** Windows' ordinary system mouse model is not equivalent to two wholly independent native mouse devices. A floating on-screen object by itself cannot force unrelated applications to accept new pointer input. The right strategy is reliable Pocket-owned interaction + selective, tested native accessibility actions. UIA provider support, focus behavior and process integrity determine where external actions work. [S03][S04][S05][S10]

### Definitions used consistently

- **Verified in documentation:** documented by the authoritative API vendor; does not mean our code has passed on Windows.
- **Design mitigation:** plausible architecture that still requires implementation and measurement.
- **Not verified:** needs an explicit test on actual target OS/hardware.
- **Unsupported by design:** intentional safety/compatibility boundary, not a bug to bypass.
- **Release blocker / P0:** cannot ship a feature with this failure.
- **P1:** should be resolved before general beta; may be acceptably limited in an early proof of concept.
- **P2:** enhancement or later-stage compatibility/performance optimization.

## 2. Deep dive: overlay transparency, mouse passthrough and focus

### Research finding

Microsoft's Window Features documentation specifically describes how **layered** window hit-testing depends on transparency and how `WS_EX_TRANSPARENT` with `WS_EX_LAYERED` passes mouse events to underlying windows. This is stronger evidence than assuming `WS_EX_TRANSPARENT` by itself is a universal magic flag. [S01]

However, WPF creates/manage its own HWND and rendering tree. Click-through **and** activation are separate concerns. The app must confirm actual extended styles and observed mouse/focus behavior on Windows 11. Transparent pixels alone are not a complete focus contract.

### Revised window topology

- `GhostOverlayWindow`: a top-level per-selected-monitor layered / no-activate / mouse-pass-through host with **only** visual GHOST, shelf, light hints. **No physical mouse click handlers** during passive Peek.
- `PocketWorkspaceWindow`: an ordinary, focusable WPF window with normal mouse and keyboard input and separate application-level GHOST routing. This is where dual drag/cooperative testing lives.
- `CaptureSelectionWindow`: only shown on explicit capture; sits on a **frozen image of the screen** after the overlay has been hidden, so the real mouse can draw a selection with deterministic coordinates.
- Avoid a full-screen native overlay controlling third-party targets via low-level hooks or synthetic `MouseDown`. That is not a genuine independent mouse.

### Concrete design rule

GHOST's own pointer hit-test should use **Pocket-owned geometry** in normalized screen physical pixels. The OS mouse passes through the overlay. No WPF `RaiseEvent(MouseDown)` simulation for hand events.

### Test sequence

1. Inspect `GetWindowLongPtr` extended styles and log overlay HWND, z-order and DPI awareness.
2. With overlay visible, drag a text selection in Notepad, drag a browser scrollbar, select files in Explorer, and type into an editable field.
3. Reveal the Pocket shelf while maintaining a real mouse drag. Verify real drag retention and `GetForegroundWindow` staying stable.
4. Toggle topmost and apply monitor scaling; confirm no lost clicks; close and reopen the app while another app is active.
5. If failing, fix topology/native styles before proceeding; don't call it a webcam problem.

## 3. Deep dive: Windows UI Automation is a semantic adapter, not a second mouse

### Additional gaps found

1. `AutomationElement.FromPoint` expects **physical desktop coordinates**, not WPF DIPs. The returned element may be a logical ancestor or not clickable at the chosen pixel. [S06]
2. Providers expose **different patterns**: buttons may use `Invoke`, checkboxes `Toggle`, lists `SelectionItem`, sliders `RangeValue`, scroll areas `Scroll`. `Invoke` is **not** a universal click. [S07]
3. Some lists **virtualize** their off-screen items, so targets may not exist in the tree until realized. Invalid/stale elements can return `UIA_E_ELEMENTNOTAVAILABLE`. [S16]
4. Automation providers can hang a caller; Microsoft recommends separating UIA work from UI thread and using an MTA thread for desktop-wide clients. [S03][S04]
5. **Focus preservation is not guaranteed**: invoking a control may trigger a new dialog/window or change target state. [S07]
6. **Security barriers are intentional**: UIAccess and elevated app interaction require conditions not appropriate as a shortcut for a normal utility. [S05][S08]

### Safer external action transaction

`Hand hover → candidate hit test → validate target → show precise capability → pinch confirmed → revalidate HWND/PID/element/action → execute worker command → inspect postcondition / report uncertain`.

- Cache only metadata for a short lifetime. Prefer control patterns to pixel hitbox imitation.
- Actions must be allowlisted, e.g. non-destructive `Invoke` on a known fixture button, `Toggle`, `Scroll`, `RangeValue` with strict min/max checks.
- Do not dispatch actions on a password field, privileged dialog, payment confirmation, delete button or unknown target in experimental mode. Don't build a privileged-UI bypass.
- Query the underlay with a **controlled test fixture**, because overlay hit-testing/UIA and Win32 window hit-testing don't necessarily agree. If no reliable underlay lookup, **do not ship GHOST external clicking** in the release.
- Worker receives a typed `ActionRequest { requestId, targetInfo, action, timestamp, allowedWindowId }`; return structured `Unsupported`, `Denied`, `Stale`, `Timeout`, `Attempted`, `Confirmed`. Never equate `Invoke` returning to full UI success.
- UIA worker uses MTA thread without its own windows; **process** boundary permits terminating hung providers when a normal task cancellation cannot stop COM.

### Independence test that decides actual supported scope

Start an ordinary physical mouse drag in app A. Invoke a supported control in app B with GHOST. Record: actual mouse coordinates before/after, drag completion, active foreground HWND before/after, action result, error and application versions. If the action interrupts the physical mouse task, classify that **app+action combination** incompatible with Strict Concurrent Mode. Do not silently weaken the original requirement.

## 4. Deep dive: input and gesture reliability

**MediaPipe live stream is not a deterministic frame-per-frame signal.** Its `detect_async` can drop input frames to reduce latency and requires monotonically increasing timestamps; results arrive via callback and include source timestamps. [S13]

### Proposed tracker contract

Tracker process → host: `{version, sequence, frameTimestampMs, resultTimestampMs, handId, confidence, landmarks, status}`. Hand landmarks are finite numbers within reasonable ranges. The host rejects older sequences, stale timestamps, invalid numbers and unknown versions. Do not send raw camera images over IPC.

### Interaction state machine

- `PAUSED`: GHOST is inactive; camera can shut down.
- `ARMING`: deliberate explicit action/hotkey or stable gesture to activate.
- `READY`: pointer may move/hover, **no clicks without confirmed pinch**.
- `PRESS_CANDIDATE`: thumb-index distance below normalized press threshold for short duration.
- `PRESSED`: target ownership established once; a hit-test should not retarget mid-press.
- `DRAGGING`: move current owned target; no separate pinch action until release.
- `LOST`: suppress actions; terminate active drag safely after bounded timeout; require a fresh pinch before a new press.

Press and release thresholds use palm-normalized geometry and hysteresis; duration should be **timestamp-based**, never measured by an assumed number of camera frames. Filter GHOST's displayed position, but pinches must be driven by confidence + distance + time, not aggressively smoothed visual coordinates.

### Practical robustness choices

- One active hand for MVP, with a hand-selection control. If identity becomes ambiguous, **pause** rather than switching hands mid-drag.
- Calibrate to a relaxed workspace near user's torso, not large midair sweeping arcs.
- Support a clutch to recenter the mapping without moving GHOST.
- Two cursor motion modes to user-test: absolute (hand camera rectangle → screen) and relative (touchpad-like hand displacement). Default based on comfort/accuracy measurement, not visual coolness.
- Use a low-complexity one-euro/adaptive filter. Never allow prediction to **initiate** a press; prediction may only interpolate pointer rendering.
- The edge-pull reveal gesture should have deliberate activation + direction + minimum movement + cooldown to avoid unintended opens.
- Interactive Peek latches open on reveal so the user can **then pinch/select cards**; a hold-to-open gesture cannot also consume the same hand for selection. Provide separate short-lived Glance and persistent Pin actions.

### Performance measurement

Instrument: camera capture timestamp → MediaPipe result timestamp → IPC received → host state update → rendered pointer time. Report median/p95 for end-to-end latency, dropped tracker frames, renderer frame time and CPU. Target threshold (not promised): median ≤120 ms, p95 ≤220 ms on the defined test laptop. Benchmark at 640×480/720p, 15/30 fps, on battery and AC.

## 5. Deep dive: screenshot capture, live windows and security

### New authoritative findings

Windows.Graphics.Capture uses a **system picker** and a system-drawn capture border under common configurations. Capture support can be unavailable based on device/source constraints. Requests for borderless capture have additional consent/capability requirements. [S14][S22]

Microsoft's display-affinity API permits a process to set `WDA_EXCLUDEFROMCAPTURE` on **its own top-level window** in supported Windows builds. This may help exclude the GHOST overlay from capture. It is not a guarantee that every capture tool respects it and is **not** a content-protection bypass. [S15]

DWM thumbnail APIs establish a preview relationship between source and destination windows; they are useful for later live references but not an automatically interactive, extracted app fragment. [S23]

### V1 capture contract (intentionally limited)

1. Explicit user activation; no background screen recording.
2. Hide GHOST/Pocket overlay and wait for composition to settle before freezing a frame; optionally apply capture-exclusion affinity to our own overlay as a supplemental defense.
3. Capture selected display/source through supported Windows API; show a still image in a normal, focusable selection window.
4. User draws rectangle with real mouse; validate nonzero dimensions and screen bounds.
5. Crop in RAM, then persist **only the crop** if the user chooses Save; use per-user local app data folder and atomic manifest updates.
6. The full frozen frame is never written to disk in normal operation, is freed promptly, and is never transmitted to a server.
7. Redact/avoid personally sensitive test fixtures; do not collect diagnostics including screenshots by default.
8. For `Temporary Pocket`, hold only in memory and discard on app exit.

### Deferred types and clear states

- `Snapshot` — fully supported in v1 after tests.
- `Live Preview` — later; source window capture/minimized behavior/DRM and app refresh verified per source.
- `Video` — later; supported embed/official player with explicit source, not assuming arbitrary YouTube crop becomes a separately controllable live player.
- `Text/URL Reference` — a possible accessible companion card, but don't invent source URL from a screenshot.

### Protections not to undermine

Never suggest disabling UAC, reducing the screen-capture border without consent, bypassing DRM/secure surfaces, or manipulating protected desktop. An unavailable content source must remain unavailable with clear feedback.

## 6. DPI, multiple monitors and desktop-state traps

- Declare Per Monitor V2 DPI awareness **before creating a window**, ideally using the manifest. Changing process DPI context after initialization can fail. [S09][S17]
- Treat coordinates as named types: `CameraNormalized`, `VirtualScreenPhysicalPx`, `MonitorLocalPhysicalPx`, `WpfDip`. Centralize transforms and include inverse round-trip tests.
- `AutomationElement.FromPoint` explicitly uses **physical** desktop coordinates. Don't feed WPF DIP points directly. [S06]
- A second display may sit **left/above** primary and have negative desktop coordinates; bounds checks should use the selected monitor's actual rectangle, not assume origin (0,0).
- Changing display scaling/resolution/rotation can invalidate calibrated geometry and stored Pocket positions. Recompute or request recalibration, clamp saved cards to the chosen monitor.
- Different monitor refresh rates and variable frame rates make frame-count-based timing unreliable; use monotonic timestamps and display-time animation updates.
- Detect screen lock, session disconnect, sleep/resume and camera device changes; pause GHOST and cancel held targets. Do not try to display over secure desktop.
- V1 should support **one explicitly chosen display** reliably. Multi-monitor is an enhancement gated by physical-coordinate tests.

## 7. Privacy, accessibility and threat model

### Privacy commitments

- Webcam is **off by default** until the user opts into hand control; clear in-app active indicator and easy pause control.
- Local inference only; **no camera frames recorded or uploaded**.
- Explicit capture command; no passive screen scraping or always-on screen capture.
- User can see, delete, export and purge stored snapshots. Temporary captures are RAM-only.
- Logs record only timings, versions, action states, error codes and non-sensitive identifiers. Avoid filenames, untrusted element text, URLs and screenshot content by default.
- Restrict IPC to same-user local communication with bounded payloads; validate all JSON/IPC and never execute a path or command from element metadata.
- Protected/secure controls are not action targets. Dangerous or destructive operations are not automatic.

### Accessibility / everyday usability

- Full keyboard/mouse alternative to capture, reveal, pin, move, delete and settings.
- Reduced motion support: OS setting disables decorative spring/rebound effects; important state changes remain clear.
- Large accessible GHOST targets and distinct labels or shapes, not only color differences.
- Gesture-only functionality should **never** be essential to retrieving a saved note.
- Don't automatically launch camera at Windows startup unless user explicitly opts in.

### Windows privilege note

Windows UIAccess is subject to special security, signed binaries, secure installation and legitimate accessibility purposes. It is **not** our workaround for accessing elevated applications. We retain standard process integrity, and the secure desktop is out of scope. [S05][S08]
